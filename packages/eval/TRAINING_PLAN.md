# Proposed training plan for the educational content reviewer

Prepared 25 October 2026. This is a proposed GPU-backed experiment following the team's new access to NTU resources. No training job has been launched. The current application remains the single-pass course-generation baseline.

Constraint update: the team cannot label its own training/evaluation dataset. The proposed path below uses existing public annotations. It can establish performance on those public tasks, but cannot establish agreement with experts on this project's adult courses or actual learner gains. Course-level educational judgments therefore remain advisory.

**Recommendation: use `Qwen/Qwen3.8-27B` as the main evaluator candidate, with `Qwen/Qwen3.5-9B` for the first supervised LoRA pilot and as the smaller deployment comparison.** The supplied guide confirms an H200 compute pool, making a 27B adapter experiment worth profiling. Start with prompted baselines and a resumable 9B pilot before the main 27B run. Select adaptations using held-out public labels for each supported task, not general model benchmarks or training loss alone. Record the adult-course transfer gap explicitly. Neither single-GPU training fit nor an educational-quality advantage has been measured.

The same banner says the cluster can store and process open data only; this plan therefore uses public, appropriately licensed training materials rather than private course uploads or learner records.

**PBS execution for the four-hour queue**

1. Connect using `ssh <NTU_ID>@gaas.hpc.ntu.edu.sg`; the guide requires the institutional VPN when off campus. Use the project's assigned code rather than an example administrator account.
2. Inspect `menu.sh` for storage quota, project membership and expiry; inspect `qstat -Q` and `pbsnodes -aSj` for current queues/resources. These guide commands identify live configuration; they do not reserve GPUs.
3. Inspect `/usr/local/templates/*.pbs` and the PyTorch examples there. Copy the relevant local template to the experiment directory and preserve the cluster-specific environment setup. In particular, the distributed test's `hpc_admin` project is not a substitute for this project's code.
4. Begin with a proposed single-node, single-GPU allocation: `#PBS -q gpu_free`, `#PBS -P <PROJECT_CODE>`, `#PBS -l walltime=04:00:00`, and `#PBS -l select=1:ncpus=4:ngpus=1`. Add an appropriate host-memory request using the template and measured requirements. This is a proposed request, not a confirmed quota. Do not put angle-bracket placeholders into the submitted script.
5. The guide lists `module load anaconda/2025` and `module load cuda/13.0`. Inspect `module avail` and build a separate pinned training environment compatible with the actual driver and training stack. Loading a CUDA module alone does not establish PyTorch/kernel compatibility. Activate the environment explicitly in the PBS script.
6. Stage public datasets and model files in verified persistent storage, using the guide's data-mover workflow where appropriate. Keep model caches and all resumable checkpoints outside ephemeral job-local paths. Do not assume a storage path or retention guarantee absent from this guide.
7. Submit with `qsub <experiment>.pbs`; monitor using `qstat -u "$USER"` and `qstat -f <JOB_ID>`. For the first job, measure a representative training batch, peak GPU memory, throughput and checkpoint duration; save, stop, resume and reload the adapter before extending training.
8. Budget each run below four hours, including startup and checkpoint writing. Initially aim for checkpoints approximately every 10-15 minutes, converting to step counts after measuring throughput, and reserve about 20 minutes for a clean final save. Implement a trainer-side elapsed-time callback that checkpoints and exits before that deadline, or a measured stop cutoff that leaves the same margin. Adjust both intervals from actual save times. PBS walltime termination is not a checkpoint strategy; the clean-stop mechanism must be tested in the pilot.
9. Continue in a new job using a complete checkpoint containing adapter, optimizer, scheduler, trainer and RNG state. Verify that the global step continues correctly. Keep the experiment's total training steps/epochs, learning-rate schedule, dataset snapshot and preprocessing fixed across jobs; use the stop callback to limit each job rather than resetting `max_steps` or warm-up at every submission. Resuming from adapter weights alone does not restore training state. No automatic resubmission is implemented or implied by this plan.

Start on one GPU to simplify debugging and conserve queue capacity. If profiling justifies more GPUs, first verify that the free queue and project permit the request. The guide's multi-GPU test uses NCCL/HPC-X and one MPI rank per GPU; adapt the institution's template and verify compatibility with the chosen training launcher. Do not wrap a launcher that already spawns GPU workers in an MPI command that spawns them a second time.

Qwen3.5-9B and Qwen3.8-27B have hybrid DeltaNet/full-attention architectures. Their native long-context support is not a training-memory guarantee. Begin the environment pilot with text-only Feedback Collection/RAGTruth examples and language-model adapters, keeping vision components frozen. A LecEval adaptation must then supply actual slide images and transcripts through the multimodal template; do not strip its images and reuse the same visual-alignment ratings as if they were text-only labels. Its input/memory profile needs a separate check. A frozen vision encoder can still process images while language adapters train.

Use original Hugging Face post-trained checkpoints, not Ollama tags, GGUF files, FP8 inference exports, or the `-Base` pretraining checkpoints. Keep exact model and tokenizer revisions in the run manifest. Begin with non-thinking supervised outputs containing concise, evidence-backed rationale and structured results. Use each model's correct template; Qwen3.8 has a dedicated template and different historical-thinking behavior. The [model-specific training recipe](https://github.com/modelscope/ms-swift/blob/main/docs/source_en/BestPractices/Qwen3_8-Best-Practice.md) documents these differences.

**Training task**

The reviewer receives a frozen learner/course brief, required-content map, intended outcomes and cognitive demand, exact source passages, generated lesson/notes/quiz, and relevant course context. It assesses one criterion or closely related criterion group at a time.

Validate the complete serialized input before making a comprehensiveness judgment: every requirement being judged, its source evidence and the candidate teaching/assessment content for that scope must remain visible. A 4K-8K limit may not accommodate a whole course. Create scoped cases with explicit requirement IDs and aggregate their coverage, or increase the profiled context budget. Do not silently truncate evidence or treat content outside the supplied review scope as missing. Keep course-wide sequencing and cross-lesson coherence as separate cases with sufficient course context.

Training targets are the published judgments/feedback rather than the candidate lesson text. Use only fields supported by each dataset. The proposed LMS inference contract is richer: criterion ID, applicability, rating/verdict, affected teaching or assessment blocks, supporting source/content passages, missing requirement IDs, concise explanation, and suggested correction, including insufficient-evidence cases. Several of those fields lack matched public supervision, so record them as prompted model outputs and validate their schema/references in code; do not manufacture expert labels to populate them. Keep pass/revise/escalate routing and threshold policy in application code.

The runtime rubric asks about omitted or shallow teaching, missing prerequisites, unsuitable examples, objective–assessment mismatch, question/answer defects and unhelpful feedback. Public supervision directly supports only the narrower tasks listed below. Deterministic citation existence, objective IDs and schema checks remain ordinary code. A reviewer cannot detect omitted source requirements if its reference map shares the generator's omissions.

**Public datasets without in-house annotation**

| Dataset | Available supervision | Proposed use and limits |
|---|---|---|
| [Prometheus Feedback Collection](https://huggingface.co/datasets/prometheus-eval/Feedback-Collection) | 99,952 rubric-conditioned response reviews, including a reference answer, feedback and 1-5 score; GPT-4-generated. Dataset card declares CC BY 4.0. | Main rubric-following and feedback warm-up. These are synthetic general-response reviews, not human judgments of learning quality. Preserve the reference-answer input; transfer from ideal answers to course-source references is an assumption to test. |
| [RAGTruth](https://github.com/ParticleMedia/RAGTruth) | Nearly 18,000 generated responses, source context and human-marked hallucination spans. Repository is MIT; source corpora retain their own terms. | Source-grounding adaptation: identify unsupported or conflicting spans. Preserve the distinction between unsupported information and proven falsehood, including the dataset's `implicit_true` annotations. Does not label pedagogical quality or coverage. |
| [LecEval](https://github.com/JoylimJY/LecEval/tree/main/dataset) | 2,097 slide/transcript pairs from 56 lectures with multiple human ratings for relevance, clarity, structure and engagement. MIT repository; underlying lecture-asset rights need to be retained/checked. | Closest public instructional-presentation adaptation. Use images plus transcripts and split by lecture. The ratings are not evidence of learner gains, whole-course completeness or detailed expert revision rationales. |
| [Oak MCQ MinDiff](https://github.com/oaknational/oak-dspy-mcq-eval/blob/main/data/mcq_mindiff_dataset.json) | 311 teacher-scored MCQs; question, correct answer, three distractors and 1-5 distractor-quality score. [Data license: OGL v3.0](https://github.com/oaknational/oak-dspy-mcq-eval/blob/main/LICENSE.md); code MIT. | Use first as a narrow assessment-quality benchmark and for prompt selection. Its code provides a reproducible 61 demonstration / 185 development / 65 test split; preserve the test partition and never train on all 311. A later small weight-adaptation experiment may use only permitted training partitions. Use `human_score`, not included baseline model predictions. No objective-alignment, source correctness or human-rationale labels. |

The [Learning Commons annotated CLEAR data](https://github.com/learning-commons-org/evaluators/blob/main/datasets/README.md) is an optional readability experiment: 1,097 rows with expert complexity ratings and rationales, designed around grades 3-4. Its [CC BY-NC-SA 4.0 data terms](https://github.com/learning-commons-org/evaluators/blob/main/LICENSE.md) and age-specific scale make it unsuitable as the default adult-learning quality target. Complexity is audience-dependent, not intrinsically a defect.

[SciEval](https://github.com/SciEval-Benchmark/SciEval) is the closest identified lesson-review dataset: authors report 273 K-12 science lesson materials and 3,549 criterion annotations with evidence/advice. It remains request-only; do not make the runnable plan depend on ungranted access. If obtained, preserve its science-specific rubric and source-unit groups. General QA corpora such as SciQ and Bloom-labelled questions do not by themselves supply good/bad course-review targets. Reference lesson collections likewise do not become critic supervision merely by containing human-written lessons.

No verified freely downloadable dataset in this review supplies complete adult-course comprehensiveness labels. Leave coverage, depth and objective alignment as source-conditioned rubric judgments with an explicit transfer limitation rather than inventing training labels or claiming they were learned from slide ratings.

**Public-data training recipe**

1. Freeze the initial [content scorecard](FRAMEWORK_RESEARCH.md), but mark which dimensions have matched public supervision and which remain prompted judgments. Keep a manifest of dataset revisions, licenses, provenance and original label meanings.
2. Split before training or prompt selection. Group Feedback Collection by original instruction; audit RAGTruth's official splits for source-level separation; split LecEval by lecture; keep identical/near-identical Oak question stems together. Deduplicate across partitions. Public labels allow held-out testing without asking the team to annotate new examples.
3. Reformat existing labels mechanically into task-specific training examples. Feedback targets contain the published feedback and score; RAGTruth targets contain annotated spans/types; LecEval/Oak targets contain only their available ratings. Do not generate an expert-looking rationale or source citation where the dataset does not provide one.
4. First run prompted baselines and an existing rubric-reviewer baseline where practical. Train a 9B pilot on a manageable public subset, including the clean-stop/resume test. Then compare general rubric warm-up, grounding adaptation and an educational-task mixture. Use task-balanced sampling/replay so the large general dataset does not overwhelm the small educational datasets; choose the mixture on development metrics rather than asserting a fixed optimum.
5. Train the 27B candidate using the selected recipe if the pilot and profiling justify it. Start with supervised LoRA. Prometheus Preference Collection can support a later pairwise-judgment task; directly applying preference optimisation to its preferred answers would optimise answer generation rather than the evaluator's judgments.
6. Evaluate separately on untouched public labels: feedback/rubric score agreement (synthetic labels), RAGTruth span/example detection, LecEval per-dimension human-rating agreement, and Oak score error/agreement. Use grouped confidence intervals and preserve task-specific scales. These results establish the corresponding benchmark abilities; they do not establish adult-course validity.
7. Add automatic regression cases where possible: remove a known referenced teaching block, corrupt a known answer key, duplicate a question, or break a reference ID. Such controlled perturbations test specific sensitivity and plumbing. They are synthetic checks, not substitute expert labels for subtle pedagogy or comprehensiveness.

Do not launch a large generic-data fine-tuning run solely to consume GPU access. A tuned checkpoint must beat the relevant untuned/prompted baseline on held-out public tasks to justify adoption. This plan does not require an in-house annotation pilot, new teacher-model labelling or a human-labelled project-specific test set.

For dense Qwen3.5/3.8, use the Transformers backend of [ms-swift](https://github.com/modelscope/ms-swift/blob/main/docs/source_en/BestPractices/Qwen3_8-Best-Practice.md), which explicitly documents these families. Pin a verified combination of CUDA, PyTorch, Transformers, PEFT, training library and hybrid-attention kernels. Keep training separate from the application image, which installs CPU PyTorch.

Initial hyperparameters are experimental starting points: LoRA rank 16 or 32, learning rate around 1e-4, 1–3 epochs selected on development results, gradient checkpointing, microbatch 1 with accumulation, and 4K–8K input-plus-output length. Train only on the assistant review output. Validate attention/kernel support and language-only target modules against the exact model recipe.

On an allocated H200, first profile BF16 LoRA for 9B, then 27B, using language-backbone adapters and frozen vision components. Approximately 27 billion BF16 parameters alone occupy 54 GB in decimal units; this arithmetic excludes activations, adapters, optimizer state, temporary buffers and any additional model components. It is not a measured training-memory estimate. Use gradient checkpointing and microbatch 1 initially; increase context from 4K toward 8K only after profiling and checking that decisive evidence fits. Use supported 4-bit QLoRA, sharding or more GPUs if actual measurements require them. Multiple GPUs help only when allocated together with supported communication. Do not begin with full-parameter training or a multi-node run merely because the cluster has a large total GPU pool.

Store dataset snapshots, manifests, logs, adapters and complete resumable checkpoints on confirmed persistent storage. Include optimizer/scheduler/RNG state for true training resumption. Keep a separately exported adapter for serving. Do not confuse loading adapter weights with resuming interrupted training.

**Success criteria**

Compare prompted versus tuned versions using identical held-out public cases and their original criteria. Primary measurable outcomes are RAGTruth detection precision/recall, LecEval per-criterion human-rating agreement and Oak distractor-score error; Prometheus agreement is agreement with synthetic labels. Report JSON failures and latency separately. Keep label types separate and do not combine raw scores into one overall educational-quality percentage.

For this project's unlabelled outputs, report coverage of extracted source requirements, evidence links, detected issues and controlled-regression results as provisional machine observations. Missed critical omissions, agreement with instructors and usefulness of advice on real project courses cannot be estimated reliably without corresponding labels or feedback. Do not report self-assessed confidence as calibrated reliability.

Check polished-but-incomplete, concise-but-sufficient and intentionally repetitive examples. Do not average away critical failures. A stronger course-review score does not establish learning gains; a later learner study would be needed for comprehension, retention or workplace transfer claims.

**Repository integration after model validation**

The evaluator is trained offline and served for inference during authoring; no fine-tuning is needed for each new uploaded course. Each request supplies that course's sources and context. In the four-hour free queue, use scheduled evaluation batches with stored results; do not assume this allocation can host a continuously available LMS endpoint. Keep authoring asynchronous, queue reviews when inference is unavailable, and use a separate long-running service allocation if continuous availability becomes a requirement.

The guide's open-data-only restriction also applies to inference inputs. NTU batch reviews in this plan may contain only permitted public course materials; private workplace uploads require an approved hosting environment that permits those inputs. Public training data does not change the treatment of private inference data.

| Pipeline point | Proposed behavior |
|---|---|
| Sources ingested and plan drafted | Independently extract a versioned inventory from the complete source set, with requirement IDs and exact passages. Relate it to the learner brief and intended scope; review the generated plan against it. An automatically extracted inventory is itself fallible, so describe completeness as coverage of extracted requirements. |
| Lesson and quiz generated | Send complete relevant slides, notes, source evidence, objectives and quiz/key/explanations to the reviewer. Run deterministic checks first. Store findings linked to slide/question/requirement IDs; inspect rendered slides when making visual judgments. |
| Course assembled | Aggregate requirement-to-teaching and requirement-to-assessment mappings. Identify missing explanations, prerequisite order problems, contradictions and unnecessary duplicate questions. The existing planning `coverage` field counts offered excerpts referenced and is not the finished-course completeness score. |
| Author views workbench | Show per-criterion findings, exact source/course evidence, affected blocks, suggested revision, evaluation status and model/rubric revision. Distinguish issue detected, no issue detected, not applicable and insufficient evidence. Keep normal author approval separate from model scores. |
| Draft revised | Allow a bounded targeted rewrite or author edit, rerun affected checks and course coverage, and invalidate findings for old content revisions. Preserve the original and all evaluation attempts. |

The [worker handlers](../../services/worker/handlers.py) already define `CRITIQUE_ASSET` and `EVAL_RUN` as stubs. Use them for repeatable asset/course review without regenerating every course. The [critique helper](../../apps/api/app/core/generation/critique/service.py) needs richer scope/evidence inputs and criterion-level outputs. Add explicit quiz-to-objective IDs; existing accepted questions omit these links. Preserve each dataset's score/rubric semantics instead of placing incompatible scores directly into the three existing score columns.

For PBS inference, add an external-review lifecycle rather than blocking a synchronous application worker during cluster queueing and execution. A handler should export the immutable review input, submit the scheduled batch and return; a later poll/import step records pending/running/completed/failed status and validated results. Track scheduler job ID, expected item IDs and content revisions, with explicit handling for partial output, walltime expiry, retry and stale results. The existing worker's stale-job window must not be treated as the lifetime of an external PBS job.

Add reviewer-specific model/endpoint/context settings rather than replacing the current generation `LLM_*` values. Extend the input/result contract with required-content IDs and criterion evidence; add assessment-to-objective links. Preserve context-budget guards on every retry and per-run accounting for both clients. Store immutable evaluation attempts with model/adapter/rubric/source revisions.

Deploy through an OpenAI-compatible serving endpoint such as a verified vLLM configuration. Start in shadow mode, then connect successful results to the currently scaffolded critique/evaluation jobs. Keep the training process outside the ordinary course-generation worker.
