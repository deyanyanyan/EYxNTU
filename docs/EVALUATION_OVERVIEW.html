02 · What the layer does

A scorecard after generation, not a gate inside it.

Evaluation reads a captured run and reports evidence about its quality. It does not launch generation, edit a lesson, approve content, or decide what happens next.

01

Saved run bundle

Lessons, quizzes, source evidence, prompt snapshots, model settings, and run metadata.

What was generated?
02

Two kinds of checks

Stable rule-based diagnostics plus optional Gemini scores for grounding, coherence, and pedagogy.

What can we observe?
03

Reviewable report

Lesson-level scores, findings, course patterns, and available model usage in the Admin Evaluation page.

What should we inspect?
● The benchmark reports. People choose.

There is no pass/revise verdict, automatic critique, or workflow action. Any future critique-and-revision loop will be tested as a separate generation condition and scored afterward by this layer.

03 · What we can test next

A controlled path from diagnosis to improvement.

Change one part of the system at a time. Keep the benchmark as the common measurement layer while the generation methods evolve.

STEP 01✓

Calibrate the benchmark with EY

Agree on quality examples, have SMEs review a blind sample, expand beyond four lessons, and keep a held-out set for later comparisons.

Make scores trustworthy
STEP 02◈

Compare model baselines

Run selected open models on the same benchmark inputs and current pipeline. Compare quality by dimension, then add speed, memory, and usage.

Model comparison
STEP 03✎

Optimize prompts and templates

Try clearer lesson scope, objective-to-quiz alignment, worked examples, and guided practice while holding model and evidence constant.

First quality experiment
STEP 04⌕

Investigate the RAG pipeline

Log retrieved passages and ranks. First test whether expected evidence is retrieved; tune chunking, ranking, or evidence packing only where gaps appear.

Measure retrieval separately
STEP 05⟳

Test agentic critique

Compare single-pass output with one bounded critique-and-revision pass. Score draft and final versions; track extra calls, time, and usage.

Separate workflow arm
STEP 06⌁

Optimize runtime; tune weights last

Compare quantized and full precision versions of the same checkpoint. Consider LoRA or lightweight fine-tuning only with approved data, examples, and compute.

Efficiency · conditional training
The experiment recipe

Make each result comparable.

Before calling an optimization an improvement, keep the inputs and scoring method stable and inspect both quality and operational trade-offs.

1Freeze the benchmark inputs and baseline configuration.
2Change one method or setting; name the experimental arm.
3Capture the output and provenance in the same run-bundle format.
4Score with the same rubric; review examples with people.
5Compare per-dimension results, errors, latency, and usage.
6Repeat finalists; keep the holdout untouched until comparison.
With EY · Align before tuning

What should “better” mean?

Use the first report as a discussion starter. Agree on the target quality and the evidence needed before choosing which experiments deserve time.

  • Which teaching and content failures matter most?
  • Who can review a blind sample and calibrate the rubric?
  • Which sources can be sent to hosted models?
  • Which models and hardware should be compared first?
  • What quality / latency / memory trade-offs are acceptable?
  • Is fine-tuning in scope, and what data can support it?
